# Build Checklist

Build mode: autonomous implementation with frequent small Git commits.
Verification: verify every tool independently, then verify the complete multi-tool journey.
Git cadence: one meaningful challenge milestone per commit whenever practical.
Submission goal: make the agent workflow visible and impressive within the first 15 seconds of the demo.

- [ ] **1. Scaffold standalone Challenge Edition**
  Spec ref: `spec.md > 1. Architecture`
  What to build: React + TypeScript + Vite application isolated from production with basic judge-facing layout and WebMCP readiness indicator.
  Acceptance: App runs locally, no production credentials are required, and non-WebMCP browsers show a useful compatibility message.
  Verify: Install dependencies, run build/test, open app locally.

- [ ] **2. Create domain model and sanitized property dataset**
  Spec ref: `spec.md > 6. Data-provider abstraction`
  What to build: Typed property domain models, realistic sanitized Thessaloniki demo inventory, and demo provider with search/get-by-id behavior.
  Acceptance: Dataset can satisfy the headline demo query with at least three credible matching candidates.
  Verify: Unit tests for filtering and lookup; manual inspection of returned candidates.

- [ ] **3. Implement `search_properties` WebMCP tool**
  Spec ref: `spec.md > 5. Tool contracts > search_properties`
  What to build: Validated structured search schema, provider integration, bounded result count, visible UI state update, structured tool response.
  Acceptance: Agent can discover and execute search; invalid ranges fail safely; no-results is represented correctly.
  Verify: Unit test search logic and manually invoke in WebMCP-enabled environment.

- [ ] **4. Implement `get_property_details` WebMCP tool**
  Spec ref: `spec.md > 5. Tool contracts > get_property_details`
  What to build: Public detail retrieval with missing-data handling and canonical URL support.
  Acceptance: Valid IDs return normalized facts; invalid IDs return controlled errors; private data is not exposed.
  Verify: Tests for valid/invalid IDs and manual tool call.

- [ ] **5. Implement transparent property comparison engine**
  Spec ref: `spec.md > 5. Tool contracts > compare_properties`
  What to build: Deterministic comparison/scoring logic for 2–5 properties, user priorities, tradeoffs, and missing-data warnings.
  Acceptance: Scores can be explained from property facts and priorities; no LLM-generated facts or hidden scoring.
  Verify: Unit tests covering price, space, renovation, proximity priorities, ties, and missing values.

- [ ] **6. Implement `compare_properties` WebMCP tool and comparison UI**
  Spec ref: `spec.md > 7. UI requirements`
  What to build: Register comparison tool, connect engine, and visibly render the comparison generated by a tool call.
  Acceptance: A judge can see the agent-triggered comparison appear in the app with clear strengths/tradeoffs.
  Verify: Execute the headline search + comparison sequence in WebMCP-enabled browser.

- [ ] **7. Implement `save_favorite` with session-safe state**
  Spec ref: `spec.md > 5. Tool contracts > save_favorite`
  What to build: Local/session favorite state with idempotent save behavior and visible favorite indicator.
  Acceptance: First save and repeated save are distinguishable; invalid property IDs fail safely.
  Verify: Unit tests plus repeated manual tool calls.

- [ ] **8. Implement `prepare_enquiry` and human review boundary**
  Spec ref: `spec.md > 5. Tool contracts > prepare_enquiry`
  What to build: Structured enquiry draft tool and review panel that explicitly requires human confirmation and never silently sends.
  Acceptance: Draft is grounded in selected property/user input; response sets `requiresHumanConfirmation: true`; no network send occurs.
  Verify: Tests plus full demo sequence ending on review panel.

- [ ] **9. Add challenge-safe remote data adapter**
  Spec ref: `spec.md > 6. Data-provider abstraction > Remote provider`
  What to build: Optional adapter to a narrow public/challenge-safe FreeSpirits endpoint with demo fallback.
  Acceptance: Challenge remains fully runnable without production access; remote mode exposes no privileged secrets.
  Verify: Test fallback behavior, CORS/error handling, and compare demo vs. remote contract shape.

- [ ] **10. Hardening, WebMCP evals, deployment and Devpost handoff**
  Spec ref: `spec.md > 8. Security and trust boundaries`, `9. Testing`, `10. Deployment`, `11. Submission evidence`
  What to build: Security review, full journey tests, HTTPS deployment, judge instructions, final README, screenshots, demo script/video checklist, final tag/commit evidence, and Devpost fields.
  Acceptance: Live URL works in supported WebMCP environment; public repo/license are visible; full headline workflow succeeds; under-three-minute demo is ready.
  Verify: Fresh-browser rehearsal from README instructions and final submission checklist review.
